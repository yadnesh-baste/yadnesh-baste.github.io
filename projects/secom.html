Which production runs will fail?

A semiconductor line records 590 sensor signals for every production run, and about 1 in 15 runs fails inspection. I tested how far those signals can predict a failure before it happens, using the validation a factory would actually live with.

Data
UCI SECOM, 1,567 runs, 590 sensors
Question
Rank runs by failure risk
Tools
Python, scikit-learn, LightGBM
Code
github.com/yadnesh-baste

Why this problem

At PowerCo I worked with sensor data from battery production, checking whether machines were ready to run. SECOM is the public dataset closest to that work: real signals, many missing values, and very few failures. In my master's programme I first met it as a classification exercise. Here I redid it properly.

The trap in this dataset

Only 104 of 1,567 runs failed. A "model" that passes every run is 93% accurate and useless. Many write-ups also shuffle the runs before splitting, so the model trains on runs from the future and is tested on the past. That leaks information a factory never has.

I measured the model by the question the quality team cares about: if we can only inspect a share of runs, how many failures do we catch when we inspect the riskiest first?

What I did

Cleaning. Dropped sensors that are more than half empty or never change, filled the remaining gaps with the median, and removed near-duplicate sensors (correlation above 0.95). 590 signals became 273. Every step runs inside the model pipeline, so it only learns from training data.

Time order. The CSV copy of the dataset had day and month swapped on some timestamps. I repaired them and kept runs in production order.

Validation. Rolling time-based cross-validation: five folds, each trained only on earlier runs and tested on the next block. That gives 1,305 test runs with 65 failures, more reliable than one small test window.

Models. Regularised logistic regression as the baseline, a random forest and LightGBM, all weighted for the rare failures.

"Caught at 10%" is the share of failing runs found when inspecting the 10% riskiest runs. Random inspection would catch 10%.

LightGBM catches about twice as many failures as random inspection at the same effort. The signal is real but modest: the 90% interval for its AUC is , so this is a prioritisation aid, not an automatic reject rule.

What I'd tell the quality team

Use the score to order inspections, not to replace them. Start root-cause work with the sensors the model relies on most (shown in the repository). The bigger win would come from data, not algorithms: labels for why a run failed, and process context such as tool, chamber and recipe, which this public dataset leaves out.

What I'd do next

Track how the score drifts week by week, add a cost-based threshold once inspection and scrap costs are known, and test simple per-sensor control limits as a transparent alternative.
